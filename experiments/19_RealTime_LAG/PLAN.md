# 実験計画: 目的4・8・32択の計測と録画同期リプレイ

作成日: 2026-10-26 JST。**以下は設計の正本。送信・計測・リプレイ・13の目的タブは実装済み。実行方法と現状はREADMEを参照。**

## 1. 目的と今回の成果物

左にLAGの録画を再生し、右にA0100・A0200それぞれの推定目的を表示する。
5stepごとの検知、後段の目的判定、API待ち時間、期限超過による欠落を、後から再生して観察できるようにする。
目的の選択肢を4・8・32個にしたときの、分類結果、到着までの時間、表示可能率、表示の安定性を比較する。

初回は**APIを別途実行して実測遅延を収集し、保存済み結果をHTMLで再生**する。
ブラウザでのライブAPI送信や動画ファイルへの字幕焼き込みは行わない。
再生中は保存済みデータだけを読むため、APIキーも不要とする。

## 2. ユーザー指定と設計上の初期値

### 指定済み

- 実験を `experiments/19_RealTime_LAG/` に置く。
- ゲート: Decisions API、`NONE / A1 / A2 / BOTH`、5stepごと。
- 有効な回答が `A1 / A2 / BOTH` なら、**どれであっても両機の目的を問い合わせる**。

- **各API呼び出しをそれぞれ3秒以内**とする。2段階合計3秒ではない。
- API送信は動画再生から分離し、実測時間を付けて後から統合する。

### この計画で置く初期値

- 後段も同じ `gpt-6-luna` のDecisions APIによる `choice` とする。自由文の本番LLMは呼ばない。
- 初回対象は18と同じ `mhi_v1.3_ic100601_win`。最初は1反復の動作確認、その後3反復。
- 入力は18と同じH=40の因果的な履歴、`[t-39, t]`。後段にも同じ窓を渡す。
- 4・8・32択でモデル、履歴、機体、質問の主目的定義を共通化する。
- 前回の目的・説明済みメモリをモデルに渡さない。選択肢数比較の途中で入力履歴依存を増やさないため。
- 初回は各ゲート陽性を独立に計測する。生成中だから次の候補を抑える制御は主実験に入れず、表示側で同一目的と古い結果を処理する。
- 分類は強制選択。32択に「判定不能」を加えて33択にすることはしない。曖昧さは人手評価に別記する。
- 入力時点で対象機が明確に非活動、または入力不成立なら `skipped_inactive / invalid_input` として目的を捏造しない。

## 4. 1つの入力窓に対する処理

```text
窓末尾step t、履歴 [t-39, t]
    ↓
共通ゲート（NONE / A1 / A2 / BOTH）を送信・計時
    ├─ NONE                                  → 後段なし
    ├─ 3秒超／エラー／拒否／不正応答          → 後段なし、理由を記録
    └─ 3秒以内の A1 / A2 / BOTH
         ├─ 条件K=4 : A0100目的 と A0200目的 を並列送信
         ├─ 条件K=8 : A0100目的 と A0200目的 を並列送信
         └─ 条件K=32: A0100目的 と A0200目的 を並列送信
              各回答を独立して計時・検証・保存
              各APIが3秒以内なら表示候補、超過なら棄却
```

3条件は3つの独立した仮想運用として比較する。6リクエストを一斉に送ることはしない。
実測時は条件を1つずつ実行し、同じ条件内の機体2件だけを並列化する。
条件順はseed=19の釣り合いを考慮したローテーションで固定・記録する。機体側の起動順も偏りを避ける。
各反復のゲートは1回だけ測定して3条件に共用し、ゲートの判定・遅延の違いを目的条件の差に混入させない。

両機とも全4機・記録済みミサイルの文脈を受け取る。対象機IDだけを変え、最初のゲートが選んだ機体集合は後段入力に含めない。
ゲートはルーティングに用いるが、後段で「A1だけ変化したはず」と誘導しない。
後段は窓末尾の目的を選ぶため、ゲート陽性を「目的が変わった」という意味に置き換えない。

選択肢は `choices/catalog.json` を正本とし、APIには対応する `choices/{4,8,32}.json` を渡す。
選ばれたIDを正本の日本語ラベルへ変換し、目的だけを表示する。理由の生成は要求しない。
各条件にはその粒度の候補だけを提示し、4択モデルに32択の一覧を追加しない。
初回は候補順を固定。候補順のランダム化は、必要なら別の頑健性実験として区別する。

## 5. 「各APIが3秒以内」の厳密な扱い

計測には単調時計を用い、SDK呼び出し直前から返却または例外までを測る。
ネットワーク、サービス側待ち、処理、SDKによる応答読み取りを含む。ディスク保存とAPI前のローカル待ち行列は別記する。
`latency_s <= 3.0` は期限内、`latency_s > 3.0` は期限超過。丸めた表示値で判定しない。

| 結果 | 後段／表示 |
|---|---|
| ゲートが2.0秒でA1 | 両機へ送信 |
| ゲートが3.1秒でBOTH | 両機とも送信しない |
| ゲート2.0秒、A1目的2.5秒 | 対象時刻から約4.5秒後にA1を表示できる |
| 同じゲート、A2目的3.2秒 | A2は表示しない。A1は取り消さない |
| ゲートまたは目的がエラー・拒否・不正応答 | 別状態で保存。NONEや目的ラベルへ置換しない |

初回計測では、3秒を超えた正常回答も診断用に保存する。HTTPの打切りは別途30秒、自動リトライ0を初期値とする。
つまり3秒は**採用期限**であり、必ず通信を3秒でキャンセルするという仕様ではない。
遅いゲートが後から陽性を返しても後段を起動しない。遅い目的回答も後から表示しない。
30秒で打ち切った場合、実際の完了時間は不明。タイムアウトまでの待ち時間を通常成功の遅延に混ぜない。

## 6. オフライン実測から再生時刻への変換

シミュレーション1倍速を基準とする。窓末尾の観測時刻を `T = 0.2 * t`、ゲート実測時間を `Lg` とする。

```text
gate_send_sim_s  = T
gate_ready_sim_s = T + Lg

goal_send_sim_s(K, aircraft) = T + Lg + dispatch_offset_s(K, aircraft)
goal_ready_sim_s(K, aircraft) = goal_send_sim_s(K, aircraft) + Lp(K, aircraft)
```

`dispatch_offset_s` はその条件の2機並列起動バッチ開始から、各SDK呼び出し開始までの実測差。
他の条件を計測している間の待ち時間や、別窓のオフライン処理時間は含めない。
実際の送信・受信UTC時刻、単調時計の差、仮想送信・受信時刻をすべて別フィールドで保存する。
実行ループ全体のwall timeを、そのまま動画の時刻へ貼り付けない。

期限超過イベントは、再生上 `call_send_sim_s + 3.0` で発生する。実際に5秒後に得た回答を使って、3秒より前に結果を出してはいけない。
期限内の回答は正確な `ready_sim_s` に到着する。既存UIの整数step表示では、その時刻以後の最初のstepで表示する。
`display_step = ceil(ready_sim_s / 0.2)` により生じる0.2秒未満の表示量子化はAPI時間と分離する。
ちょうどstep境界の浮動小数点誤差を扱い、未来の結果を先取りしない。

2段階合計は各APIが期限内でも最大約6秒＋ローカル起動差になり得る。
後段にもstep tまでの同じ履歴を渡す。返答待ちの間に進んだt+1以降のデータを、後段の入力へ勝手に追加しない。

再生速度を0.5倍・2倍等に変えても、保存した到着シミュレーション時刻と採用判定は変えない。
速度変更は閲覧の操作であり、別のAPI速度実験として扱わない。

**この方式は、測定した遅延を使う反実仮想リプレイである。**
同時実行が増えた本番サービスの負荷、1秒ごとの実送信でのレート制限、実際の待ち行列は測定していない。
オフラインの機体2件並列で得た時間を、継続的な実時間運用の達成保証には使わない。

## 7. 返答順・古い結果・重複の表示規則

目的イベントは条件・反復・機体ごとに管理し、`ready_sim_s` の順で処理する。
A1とA2の両方を待って一括表示することはしない。同着時はquery IDによる固定順にする。

1. 期限超過、拒否、不正応答、通信失敗は現在の目的を更新しない。
2. その機体ですでに採用した回答より `source_end_step` が古ければ `stale` として表示しない。
3. 同一窓・機体・条件・反復は1回だけ採用する。再読込や重複ログで再表示しない。
4. 前回と同じ目的なら現在カードの根拠時刻だけ更新し、同じ目的文を履歴へ追加しない。最新採用stepも進める。
5. 目的が変わった場合に履歴へ追加する。A→B→Aは3回の意味のある更新として残す。
6. ゲートNONEや期限超過を「目的なし」とは扱わない。直前の目的を「最終推定」と根拠時刻付きで残す。
7. 撃墜等で現在の機体が非活動なら、その時点以降は活動中の現在目的として表示しない。到着した過去窓の回答は監査ログに残す。

「同じラベル」は同じ事象である保証ではない。繰り返しの別攻撃が同じ目的を持つ場合もある。
この抑制は目的表示の重複を減らす規則であり、イベント同定の正解率を示すものではない。

初回は生成中リクエストを理由に次のゲートや目的候補を抑えない。
そのため、仮想再生では複数窓の候補が同時に実行中になり得る。最大実行中件数も出力する。
後で「1機1件の実行中制限」を比較する場合は、これと別の運用条件としてバッファ・再判定の規則を追加する。
それを主実験へ暗黙に混ぜると、Kごとに入力窓が変わり、純粋な対応比較ができなくなる。

## 10. 比較指標と評価ラベル

### 遅延と表示

- ゲート・K別目的・機体別の成功応答時間p50/p95、3秒超過率、エラー率、形式有効率。
- 全正常回答と、期限内採用回答の時間分布を分ける。期限内だけのp95で全体を代表させない。
- 共通のゲート陽性窓に対する機体別の期限内到着率。
- 両機とも表示可能／片方のみ／両方棄却の件数。全ゲート窓を分母とした値も併記する。
- 対象観測時刻→表示候補到着までの2段階遅延、UI表示量子化による追加遅延。
- stale率、連続同一目的の抑制数、目的変更回数、仮想最大実行中件数。
- 試合中に表示できた割合と、試合後の末尾区間まで含めた割合。
- 入力トークン、キャッシュ、usageに基づく費用。未報告usageは0としない。

### 目的の妥当性

既存の7イベント注釈は「変化の開始地点」であり、全窓末尾の目的ラベルではない。
そのまま全窓の4・8・32択の正解へコピーしない。
特にヒットアンドアウェーは途中で目的が変わるため、窓末尾基準で評価する。

人手で窓・機体ごとに `supported_goal`, `acceptable_alternatives`, `review_status`, `evidence` を記録する。
32択まで決められない場合は上位分類だけにラベルを付け、細分類を無理に埋めない。
モデル予測を正解として再利用せず、同じレビュー基準で各条件を比較する。

- Kそれぞれの分類一致率: ラベルが確定した対応窓のみ。分母・未確定数を明記。
- 8・32択を親へ写像した共通4分類での一致率。
- 正解ラベルなしの条件間一致率: 正確性とは呼ばない。
- 期限内かつ分類が正しかった割合: 遅延による脱落も含む運用指標。
- A→B→A等の短時間の反転: 実際の目的変化かモデル不安定かを人手確認。

主比較は**候補数と目的粒度を一緒に変える比較**であり、選択肢数だけの因果効果は主張しない。
候補の文章量も変わるため、トークン数を併記する。
3反復は同じ1試合の反復であり、独立3試合ではない。重複窓を独立標本とした汎化精度は報告しない。

## 11. リクエスト数の見積もり

18と同じ対象では窓末尾39,44,...,339,340の62窓。最後だけ1step間隔。
H=40を満たすまでの0〜38stepは初期履歴蓄積期間として新しい判定をしない。
ACMIのみの終端341はモデル入力に使用しない。

各反復で、3秒以内・有効・NONE以外のゲート数をNとすると、両機が有効な場合:

```text
ゲート:       62件
目的:         N × 2機 × 3条件 = 6N件
合計:         62 + 6N件 / 反復
最大:         434件 / 反復、3反復で1,302件
```

18の既存結果では各反復43窓がYESだったが、3秒条件を入れた19のNとは異なる。
仮にN=43なら320件/反復、3反復960件。これは見積もりであり実績ではない。
既存18のゲート結果を使う場合は `imported_gate` と明示し、実行条件の違う新規測定と混ぜない。
予算は送信計画から提示できるようにし、ブラウザ再生やexportで追加課金が発生しない設計とする。

## 12. 実装の順序と完了条件

1. **分類・計画の固定（今回）**
   4/8/32の件数・一意性・親子写像を検証して保存する。
2. **オフライン入力・プロンプト作成**
   13の検証済みCSVから18互換の窓を作り、ゲートと目的のリクエストを送信せず確認する。
3. **送信と計測**
   ゲートを共通化し、目的は機体2件だけ並列。各APIの期限・生応答・再開状態を保存する。
4. **リプレイ生成**
   保存済みの実測時間から3条件のイベントを作り、同一目的・古い結果・期限超過を適用する。
5. **13のHTML統合**
   左の録画を維持し、右に機体別の目的を到着順に表示。条件切替・シーク・末尾区間を実装する。
6. **1反復のパイロット**
   対象・問い・表示のずれを確認。修正時はプロンプト／runの版を変える。
7. **固定条件で3反復評価**
   期限内到着率、遅延、目的分類、4分類へ戻した比較、人手レビューを出力する。

必要な検証:

- 未来stepが入力に入らない。H=40、stride=5、末尾340の扱いが18と一致する。
- A1だけ／A2だけ／BOTHのいずれでも両機を送る。NONE・遅いゲート・不正ゲートからは送らない。
- 2.999秒・3.000秒は採用、3.001秒は棄却。合計が3秒超でも各呼出が期限内なら採用する。
- A1だけ期限内ならA1だけ表示する。片方のエラーで他方を破棄しない。
- 後から届く古い回答が新しい目的を上書きしない。同一目的でも採用stepは進む。
- 同一目的の連続は履歴を増やさず、A→B→Aは保持する。
- シーク、巻き戻し、条件切替、再生速度変更、終端後の待ち区間が決定的に再現される。
- 保存済み再生・再集計・exportではAPI呼び出しが0件。
- 計測と候補を固定したHTTPモックで分岐を確認後、実APIでは返答形式と時間をパイロットで確認する。
