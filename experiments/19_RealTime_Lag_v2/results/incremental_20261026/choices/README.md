# 目的の選択肢 — goals-v001

2026-10-26にユーザーが承認した4・8・32択。表示文は承認案を保持する。

`catalog.json` が正本。`4.json`・`8.json`・`32.json` はAPIへ渡す `value / description` 配列で、表示ラベルは正本から参照する。

API配列のdescriptionはラベルと定義を連結したもの。32択では親の判定範囲を補足する。選択肢の順序は正本の順序に固定する。

## 共通の問い

現在時点で、その機体が最も優先していると推定される短期目的を1つ選ぶ。

## 共通規則

- 入力窓全体を根拠に、窓末尾時点の主目的を1つ選ぶ。
- 目的が途中で変化した場合、窓全体の多数決ではなく末尾時点の目的を選ぶ。
- 選択肢は名義カテゴリであり、番号・表示順は優先順位や強弱を表さない。
- 行動の形ではなく、その行動によって達成しようとしている結果で分類する。
- 複数の利益が生じる場合、行動を選ぶ直接の理由として最も支持される主目的を選び、副次的な利益だけで分類しない。
- 囮と援護は独立した目的ラベルにせず、誰の攻撃成立・被弾防止のためかで分類する。
- 僚機への利益が生じるだけでは支援目的とせず、僚機の状況と対象機の行動を結び付ける根拠を要求する。
- 標的ID、レーダー・警報、通信、内部意図、命中結果が観測されていると仮定しない。
- 前回と同じ目的も有効な回答。目的の継続と判定不能を混同しない。
- 4・8・32個の目的だけを用意し、判定不能を追加の選択肢にはしない。初回実験は有効入力に対する強制選択であり、確実な意図の同定とは扱わない。

## 解釈上の限界

- 32択の一部は同じ行動で同時に達成できる。主目的の選択であり、実際の目的が完全に排他的だとは仮定しない。
- 細分化すると意味の重複と根拠不足が増える可能性がある。未検証のラベル体系として評価する。
- 4・8・32択は選択肢数と目的粒度が同時に変わる。候補数だけの因果効果ではない。

選択肢のIDと機体IDは別の名前空間。たとえば目的A1は「自機の攻撃機会を作る」であり、ゲートのA1（A0100のみ）とは異なる。

現在の実験計画は有効入力の強制選択。非活動・入力不成立・API拒否・不正応答・期限超過は目的とは別の状態として保存する。

目的が継続している場合も同じラベルを選ぶ。同じ目的を画面に再追加するかは再生側で制御する。
