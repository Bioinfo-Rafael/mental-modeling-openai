## 解釈と推奨タスク

### 1. 主タスクは「新たな説明の必要性」の逐次検出

推奨する問いは「時刻tまでに得られた履歴の中で、既に説明済み・説明待ちの内容に追加して、今説明を始めるべき新しい節目の根拠が得られたか」。初期の対象はA0100/A0200の注釈再現とし、入力にはBチームとミサイルも残す。Bチーム自体の説明地点まで評価対象を広げる場合は、その注釈も追加する。

初期値は履歴H=50時点、実行間隔S=5step。

```text
時刻t = 0,5,10,...,340
入力 = [max(0,t-49), t] の状態と、その時点で既知の行動
新着部分 = (t-5,t]
履歴50時点の端点間 = 9.8秒
実行間隔 = 1秒
```

ユーザー案の[n,n+50]は両端を含めると51時点・10秒。いずれでもよいが実験仕様は固定する。序盤は短い履歴を許容し、未来で埋めない。最初の50時点を待ってから始めると、46step付近の場面の即時検出を評価できない。

行動a_tが選択済みの直後に検出する条件ならa_tまで含めてよい。状態到着時点・行動選択前の条件ならa_(t-1)までに制限する。どちらでもa_tの結果はまだ使わない。実ログの取得順序に合わせ、基準時刻をmanifestに記録する。

前回までに分かっていた出来事が履歴に残るだけならNO。新着部分にある節目、または過去の曖昧な変化について今回初めて十分な根拠が得られたならYES。後者を認めることで、厳密な「最新5stepに開始点があるか」だけでは落とす遅延検出も扱える。

全試合を渡して選ばせる条件は、オフラインの比較条件として残す。こちらが成功してオンラインが失敗した場合、未来情報、長い履歴、逐次判定のいずれが効いたかを追加比較する。全試合条件だけでオンライン能力があるとは言えない。

### 2. 窓内包含ラベルで重複が増えることの計算

注釈の開始点集合G={46,49,83,95,143,243,311}だけを使い、t=0,5,...,340の69回を計算した。

| 便宜的なラベル規則 | YESになる回数 |
|---|---:|
| 過去50時点にGのどれかがある | 45/69 |
| 新着5stepにGのどれかがある | 6/69 |

後者の時刻は50,85,95,145,245,315。46と49の2件がt=50にまとまる。これはラベルの機械的な集計であり、モデルの検出性能ではない。また、開始点でのオンライン認識可能性を保証するものでもない。

### 3. 出力と重複防止

ユーザー向けのトリガーはYES/NOでよい。単純な第一実験もYES/NOだけで実施できる。ただしこれだけでは、t=50のYESが46と49の両方を捉えたか、どちらか一つか分からない。二値判定の成績と機体別イベント7件の再現率を同一視しない。

運用・診断用には小さいメタデータを持たせる案を推奨する。例えば `trigger` と候補の `aircraft_id`、`event_step` を返す。必要なら観測に即した短いevent_typeも持たせる。長い理由文や戦術名の完全一致は検出器に要求しない。

説明モデルまたは管理コードは、候補、説明待ち、説明済み、今回は不要と判断した出来事を区別して保持する。機体・出来事の開始時刻・内容を照合して重複を避け、同じ機体でも別の変化なら再発火する。発火後に全機体を10秒一律停止する方式は採用しない。

説明待ちの同一出来事は一つのジョブにまとめるが、新しい出来事は追記・別キューに入れる。モデル自身の予測履歴で逐次評価し、人手の正解イベントを毎回メモリに入れない。説明不要とされた候補も、その後新しい根拠が加わった場合は再検討できるようにする。

### 4. 予見性は分けて測る

「変化を見て説明を始める」と「変化が起きる前に始まりを予告する」は別のラベルを持つ。最初は前者を主タスクとする。後者は例えば次の10step以内に新しい節目が始まるかを、t以前だけから答える別実験にする。

履歴から生成した予測を補助入力にすることは可能だが、未確認の予測を観測事実として扱わない。15の未来10step予測との接続は後続案。16の回帰係数は評価対象のMHI試合を含む全3試合から推定されているため、そのまま未知試合での先読み評価の根拠にしない。

## ラベルと評価の設計案

### 正解の意味

最初の評価対象は「Rafaelの選択地点を再現できるか」であり、方策内部の真の意図を復元した正解率ではない。援護・囮を理解できたかは、地点を拾えたかと別に評価する。

注釈テーブルには、元の開始stepを保存した上で、オンラインで根拠が初めて見えるstepまたは許容区間、対象機体、出来事のまとまりを追記する案。未来を隠したリプレイでこれを確かめる。元注釈を上書きせず、追加ラベルとして管理する。

未注釈区間をすべて確定NOとはみなさない。まず同じ試合を最後までレビューし、追加注釈の有無を確認する。「Rafaelの既存7件への一致」という閉じた評価では未対応発火を数えられるが、それをただちに「説明不要な誤発火」と呼ばない。誤発火候補を人が見て、注釈漏れ・別解釈・真の不要発火を分ける。

### 主指標

1. イベント再現率。7件中何件を拾ったか。機体別に一対一対応させ、一つの曖昧なYESを複数イベントへの検出成功として数えない。候補一覧を出した場合は各候補を個別に対応付ける。
2. 検出遅れ。開始点から検出までと、オンラインで観測可能になってから検出までを分ける。主期限を暫定10stepとし、5/10step以内の検出件数を併記する。遅れは欠落イベントを除外して平均だけ良く見せない。
3. 未対応発火数と、人手確認済みの不要発火数。試合あたり・シミュレーション1分あたりで報告する。
4. 同一出来事の重複検出回数、重複した説明回数、説明モデル呼び出し回数。前段と後段を分ける。
5. 実時間の応答。検出器・説明器のp50/p95、キュー待ち、通知完了、入力・出力トークン数を記録する。既存Batchの処理時間からリアルタイム速度を推定しない。

二値の適合率・再現率・F2は補助指標。正解率だけでは、NOの多さや重複窓に左右される。後段が見逃しを救えないため、前段は再現率を優先し、同時に不要呼び出し数の予算を置く。always-YESも比較に入れ、全件発火で見かけの再現率だけを上げていないか確かめる。

シミュレーション等速再生なら、出来事から通知までの時間は概ね「判定機会までの待ち＋検出推論＋キュー＋説明生成」。S=5の周期だけでも最長で約1秒、S=10なら約2秒待ちうる。何を応答時間の起点とするかを固定する。

### データ分割

現在は1試合・7注釈なので、まず再現デモと失敗分析。重なった窓をランダムにtrain/testへ分けても未知場面の評価にならない。few-shot例、プロンプト調整、閾値調整にこの試合を使った場合、この試合での再測定は開発結果として報告する。

次段階では未使用試合を追加注釈してepisode単位で分割する。13には他2試合もあるが、別方策の試合であり、MHI方策の別試合と同一視せず、方策が変わる条件として扱う。時系列区間で暫定分割するときも、窓の重なりと境界周辺の文脈共有を除く必要がある。

## モデル・入力・プロンプトの実験案

### 比較する条件

| 条件 | 目的 |
|---|---|
| always-NO / always-YES | クラス偏りと呼び出し負荷の基準 |
| 観測変化の簡単なルール | LLMによる意味判断がどこで必要か確かめる |
| 大きいモデル、過去のみ、学習なし | この入力で注釈に対応する場面を判定できるか確かめる |
| 小さいモデル、同じ入力・同じ判定仕様 | 精度と速度の比較 |
| 小さいモデル、圧縮入力 | 入力負荷を削減した効果と情報損失の比較 |
| 大きいモデル、全試合入力 | 回顧的に重要場面を選べるかの補助比較 |

最初の逐次条件はH=50、S=5に固定。その後にS=10、H=30/100などを一つずつ変える。多数の条件を7件に合わせ込まない。

既存17のsol/terra/lunaは比較再現用の保存済みモデル指定であり、本ノートで現在の可用性や速度を確認したわけではない。ユーザー記載の「Jev」が指すモデルは確認できていないため、特定モデルの速度・能力を断定しない。最終選定は同じ再現率基準・呼び出し予算で実測する。

### 入力を軽くする案

全4機・ミサイルの文脈を保ちつつ、固定の列順を一度だけ宣言し、行ごとの長いJSONキーの反復を減らす。さらに過去部分を粗く、直近部分を細かくする条件を比較する。既に観測した重要な出来事を短いメモリとして保持すれば、50step窓より前の文脈も参照できる。

生数値から算出する差分・傾向はコードで計算し、原記録と派生量を区別する。過去だけで計算し、中央移動平均や未来で補完する処理は使わない。射撃・ミサイル消滅などの離散イベントは単純間引きで落とさない。入力圧縮の優劣は未測定。

### 検出器の短い指示案

以下は設計案であり、注釈7件の具体的な時刻を推論プロンプトに入れない。

```text
Use only information available at current_step.
Decide whether a newly supported, not-yet-covered development warrants
a fresh explanation of A0100 or A0200's behavior now.
Use the older history for context and focus on evidence added since
the previous check. An earlier ambiguous change may qualify if new
evidence now makes it explanation-worthy.
Do not trigger solely because an already covered event remains in the
window or because an ongoing maneuver continues without meaningful change.
Allow a consecutive trigger for a different event or aircraft.
Do not require a confident tactical-intention label before flagging a
plausible important transition for the explanation model to review.
Output only YES or NO.
```

入力にはcurrent_step、前回確認step、履歴、直近の候補・説明待ち・説明済み情報を渡す。必要なLAGの状態・行動・欠損定義は短く付ける。この規則だけで個人の選択基準を十分に学べるとは限らないため、別試合の正例・紛らわしい負例を追加し、人との一致を確かめる。

## 説明器への接続

17の「観測した行動・目的・背景をつないで説明する」指示は再利用できる。ただし既存tactical_system/userは61時点の前後窓を回顧的に読むこと、後続展開も説明すること、全4機に90〜160英単語程度で書くことを明示している。

オンライン条件では、例えば検出時刻tまでの61時点 `[max(0,t-60),t]` を渡し、現在までの観測と今後の仮説を分ける版を作る。中心時刻・後続観測・固定61時点の記述は実際の入力と一致するように変更する。旧版は回顧的比較用に保存する。イベント中心から+30stepが揃うまで待つ方式は等速再生で6秒必要になる。

説明器は候補が説明不要なら出力を抑制できるようにする。表示は先方要望に合わせて対象機体につき1文程度の「今何をしているか・なぜか」。まず過去のみの長い版で説明品質を確かめ、短い版への変更効果は別に測ってもよい。候補の機体以外の文脈も必要なので、入力は全体を保つ。

人からの質問（要求点）は二値ゲートを通過条件にせず、その時点の履歴で説明器を直接呼ぶ。自発説明の検出と、要求への応答は同じ履歴・説明済み状態を共有する。
