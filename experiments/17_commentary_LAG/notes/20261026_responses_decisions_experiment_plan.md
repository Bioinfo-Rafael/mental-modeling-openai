## 2. 全段階で共通にする入力とラベル

### 時間の定義

```text
判定時刻: t
履歴: [max(0,t-H+1), t]、初期H=50時点
判定対象区間: [max(0,t-9), t] の最大10時点
実行周期: S=5step=1秒
50時点の端点間: 49×0.2=9.8秒
10時点の端点間: 9×0.2=1.8秒（判定区間幅の呼称は10step）
```

入力範囲と判定対象区間をヘッダーに別々に書く。例えばt=145なら96〜145を渡し、136〜145の開始・変化を問う。96〜135は背景であり、そこに古い重要イベントがあることだけではYESにしない。全4機と記録済みミサイルを文脈として渡すが、説明必要性の対象は注釈のあるAチーム2機に限定する。

全体評価はt=0,5,...,340の69窓。t<49は得られている短い履歴で判定し、未来や0で埋めない。序盤の短い履歴の成績を別掲する。

### 何を見せるか

17と同じ状態10成分、移動行動3成分、識別・生存・可用性・記録イベント・記録された残弾数を基本とする。shoot_action、missile_launched、effect、controller種別、勝敗入りepisode名、将来の記録、注釈文、注釈step一覧は渡さない。欠損・無効状態のマスク規約も17から継承する。

最初は行動a_tが選択済みの直後に検出を呼ぶ条件とし、s_tとa_tまでを提示する。a_tの結果は提示しない。これが実運用の取得順序と合わない場合は、全比較条件でa_(t-1)までに統一する。射撃の記録と観測の1step差をラベルの取り違えと混同しない。

同じ時点の同じ列を両APIへ渡す。API比較の初回は同じシリアライズ済みテキストを使い、一方だけinput_jsonや追加特徴量に変えない。ファイル名やcase_idにpositive/negativeを含めたまま推論入力へ送らない。履歴・問題・選択肢を共有部品として固定し、そのhashを記録する。

### 正解の意味

イベント開始stepが判定対象区間に含まれれば、既存注釈に基づく暫定ラベルはYES。ただしこれは「動画で選んだ開始地点がある」というラベルであり、その時点で注釈の解釈全体がログから分かる保証ではない。

区間に注釈がなければ `negative_candidate` とする。ユーザーの注釈が全変化を網羅するか未確認なので、レビュー前に「確定した説明不要」と呼ばない。実行前に全69窓を見直し、YES/NO/判定保留とその根拠を固定する。モデルの回答を見てから都合よく正解を変えない。注釈漏れを後で発見した場合はラベル版を更新し、全条件を同じ版で再採点する。

### リクエストと出力

- `model=gpt-6-luna`、`reasoning.effort=low`、Responses、通常のオンラインリクエスト。Batchを使わない。

出力形の例（実際のモデル回答ではない）:

```json
{
  "decision": "YES",
  "events": [
    {
      "aircraft_id": "A0100",
      "event_step": 243,
      "evidence_steps": [242, 243, 245],
      "reason": "直前までの機動から切り替わりが見られ、行動の説明を更新する必要があるため。"

```

### 誤りの分類と根拠の検証

1. YES/NOの誤り。
2. 機体違い、または開始stepの位置違い。
3. 古い出来事を新しいものとして拾った。
4. 微小な調整や同じ動作の継続を重要変化とした。
5. 動作変化は拾ったが、援護・囮等の目的の確定を要求してNOにした。
6. 入力数値・時刻の読み違い、欠損の誤読、将来情報の捏造。
7. 注釈の曖昧さ、注釈漏れ、現在の入力では認識できない可能性。

理由はモデルの報告した根拠であり、内部の判断原因の観測ではない。引用された値・時刻をCSVと照合する。原因仮説は、次段階で特定の指示や入力長だけを変更して同じ問題を再評価して検討する。理由がもっともらしいだけで原因を確定しない。

## 4. 段階2：Responsesでプロンプト・選択肢・入力長を改善

### 2A. プロンプトと選択肢の説明

H=50、対象10step、段階1の24窓を固定。最大3案を比較する。

| 案 | 変更点 | 検証したい仮説 |
|---|---|---|
| P0 | 基本の「説明すべき開始・変化か」 | 基準 |
| P1 | P0に、古い出来事の残存・微小調整・継続をNOとする区別を追加 | 過去イベントへの重複・継続への誤発火が減るか |

## 5. 段階3：Decisionsで同じ問題・選択肢を評価

### 一対一比較

- 対象は段階2Cと同じ69窓、同じP*・H*・選択肢。
- Decisionsは1窓1リクエスト、1個のchoice質問。選択肢は同じ文字列 `YES` / `NO` と同じ説明文。
- 3反復で207リクエスト。ResponsesはR_shortを比較対象とする。入力テキストのhashとcase_idで突き合わせる。
- `choice`、各選択肢の確率、confidence、usage、エラーを保存する。まずAPIが返すchoiceをそのまま採点し、後から都合のよい確率閾値に変えない。
- 二値選択肢の順序も揃える。実験中に一方だけ順序や定義を変えない。

DecisionsにはResponsesと同じreasoning.effort指定がないため、同一推論量の比較とは主張しない。同じモデル名・意味的な問題・選択肢での利用結果を比較する。入力のAPI包装や回答方式までバイト単位で同一にはできない。

### 指標

窓単位の混同行列、YES recall/precision、NOの誤発火率、balanced accuracy、F2、無効・拒否・APIエラー率、反復で答えが変わる率を報告する。API間の一致率だけでは正しさは分からないため、両方誤答・片方だけ正答・両方正答の件数を併記する。

機体とevent_stepを出さない二値比較では、t=50のYESだけで46と49の両方を検出したと数えない。7イベント個別の再現率・±2stepの暫定位置許容・機体一致はR_diagの診断指標。二値版は窓分類と、あらかじめ固定した6時間帯（46/49を1場面、残り5件を各1場面）の捕捉率までを報告する。最終的な7件の再現は説明器の出力を含めて確認する。

### 閾値と未使用試合

見逃し優先の閾値が必要なら、主比較とは別の運用条件として開発セットでP(YES)の閾値を選ぶ。候補は0.1〜0.9の0.1刻み、全9候補。precision/recallと呼び出し数をすべて報告する。confidenceはYESの確率と同一視しない。閾値は未知試合の結果を見る前に固定する。少数例での確率較正の良さは主張しない。

## 6. 段階4：レイテンシ・料金・精度

### 4A. 同一問題でのAPI比較

R_shortとDecisionsを比較する。P*・H*・選択肢・モデル・標準の処理条件・実行クライアント・地域・同時実行数1を固定。各API69窓×10反復=690、両API合計1,380リクエストを初期計画とする。段階3の測定を単純流用せず、同じ測定セッションで対にしてAPI順序を交互または乱数で割り当て、順序を保存する。

理由付きR_diagの時間は参考値として別掲する。診断版とDecisionsの時間差を主たるAPI高速化率として出さない。必要ならR_shortのreasoning.effort=noneを追加条件にするが、lowからの精度変化と別に報告する。

| 記録 | 定義 |
|---|---|
| API応答時間 | 送信開始から完全な判定を解析できるまで。最初のトークンまでではない |
| p50/p95・最大 | 両APIそれぞれ。試行数と失敗数を併記 |
| 失敗・再試行 | 初回の失敗率と、再試行を含む完了までの時間を分ける |
| 準備時間 | 履歴抽出・シリアライズ・検証をAPI応答時間と別に記録 |
| キャッシュ | input/cached/cache_write/output/reasoningのusageを保存 |
| 費用 | 1,000判定、1試合、等速再生1分あたり。後段説明器の費用は別項目 |
| 精度 | 同じラベル版で再採点し、高速化条件で変わっていないか確認 |

69窓を1試合として扱い、690回を独立した690場面とは扱わない。balancedな24窓の率を本番のYES率とみなさず、全69窓で呼び出し数・費用を計算する。

キャッシュは初回と繰り返しを分ける。初回でもヒットする可能性があるので、usageに基づいてmiss/read/writeを分類する。同一窓の反復ヒットと、窓がずれる実運用で共有prefixだけがヒットする条件を区別する。キャッシュを確実に無効化できると仮定せず、入力への無関係な文字追加で条件を変えない。

2026-10-26時点の公式標準料金は6 lunaで未キャッシュ入力$0.10、cache read $0.01、cache write $0.125、Responses出力$0.50（いずれも100万tokenあたり）。Decisionsは出力課金なしで、cache料金は同モデルの標準料金に従う。地域・長文・処理tier等の条件を別に記録し、実行日に再確認する。[モデル料金](https://developers.openai.com/api/docs/models/gpt-6-luna)、[Decisions料金](https://developers.openai.com/api/docs/guides/decisions)

I=usage.input_tokens、R=cached_tokens、W=cache_write_tokens、O=課金対象output_tokensとして、上記標準条件では概算は以下。R/WはIに含まれ、二重加算しない。

```text
Responses費用 = ((I-R-W)*0.10 + R*0.01 + W*0.125 + O*0.50) / 1,000,000
Decisions費用 = ((I-R-W)*0.10 + R*0.01 + W*0.125) / 1,000,000
```

usageの定義・単価が実行時に変わった場合は更新する。reasoning_tokensがoutput_tokens内に含まれる場合は別加算しない。HTTP/SDKのオーバーヘッド込みの時間を測る。429・拒否・打ち切りをNOに置換しない。

### 4B. 逐次運用と説明器への接続

静的比較の後、同じログをS=5stepで逐次再生する。S=10stepの条件も追加できるが、判定機会自体が減るため別の運用条件として報告する。

対象10stepと周期5stepは重なるため、独立窓では同じイベントへのYESが2回出ることが正常である。これは重複した説明を2回表示してよい意味ではない。説明器が返すイベントの機体・開始step・内容を使って、候補・処理中・説明済みを管理する。別イベントなら連続YESを許し、全機体の一律停止時間で抑えない。

メモリありの運用では「まだ処理・説明していない重要変化か」という新しい条件が加わる。両APIの問題文を同じように変更し、静的な窓包含ラベルで採点しない。モデル自身の履歴でリプレイし、人手正解を説明済みメモリとして投入しない。APIごとに履歴が分岐するため、4Aの同一入力比較とは別に扱う。

後段の説明器とプロンプトは両系で同じに固定し、前後30step版ではなく現在までの履歴で説明する。説明器のモデル選定は今回の「検出器6 luna固定」と分ける。説明済みイベントを返す形式や同時発生イベントの扱いは、結合時に実装・検証する。

合計費用は「検出器の全呼び出し＋YESによる説明器の呼び出し＋再試行」。Decisionsが安くてもYESが増えれば合計は増えうるため、同じ再現率または同じ呼び出し予算で比較する。説明待ちと新規変化が重なる場合のキュー処理・重複抑制も測る。

検出器の暫定目標はS=5の1秒周期に追従できること。p95<1秒は提案する運用目標であり、既存資料で合意された数値ではない。先方メールの2〜3秒は主として要求後の応答待ち時間の目安。自発通知では判定待ち・検出・キュー・説明生成を合計し、許容時間を別途定義する。

## 7. 実験の限界と終了時に残すもの

今回の元注釈は7イベント・1試合であり、重複窓や反復を増やしても独立した事例は増えない。P0/P1/P2やHを比較して選んだMHI試合の成績は開発成績。比較した候補数と全結果を残し、改善の原因や未知試合への優位性を断定しない。

各試行でraw response、共有入力hash、プロンプト・選択肢・ラベルの版、モデル名と返されたモデル識別子、パラメータ、時刻、usage、クライアント所要時間、エラーを保存する。実験計画の表には未実行・完了・保留を区別する。

成果物は、(1)ラベルを確認したケース一覧、(2)段階1の誤り表、(3)段階2の候補別比較と凍結仕様、(4)段階3の対比較、(5)段階4の精度・時間・料金表と逐次実行ログ。今回作成したのは実験計画と窓範囲のメタデータだけである。
