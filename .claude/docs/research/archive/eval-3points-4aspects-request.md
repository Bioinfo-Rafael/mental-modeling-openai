# User request (2026-11-04): Translator evaluation, 3 time points x 4 aspects

Verbatim user requirement (Japanese, kept as written so no meaning is lost in translation).
It was given as the answer to "how should the judge's overall 1-5 anchors read?", so it
supersedes that question. Related decisions: `translator-requirements.md` D42-D45.

---

現在進めている LLM as a Translator の実装に、以下の評価機能を追加してください。

## 目的

Translatorの出力を、次の「3時点 × 4観点」で評価できるようにしてください。

評価する時点:

1. 開始点：計画どおり新しい戦術を始めるとき
2. 変化点：警報・指示などの外的要因で戦術が変わるとき
3. 要求点：人から意図を尋ねられたとき

評価観点:

1. 要素
2. 正しさ
3. タイミング
4. 判断への寄与

## 最重要の時間制約

時刻 t に生成する説明には、時刻 t 以前の情報だけを使用してください。t より後の軌跡、状態、行動、結果を生成入力に混ぜてはいけません。

評価用の正解照合では将来の行動を参照して構いませんが、生成入力と評価入力を明確に分離してください。未来情報の混入を検出し、テストで防止してください。

## 1. 要素

すべての説明で、次の2要素を必須とします。

- 今何をしているか
- なぜそうするか
  - 近い将来に実現したい状況を含めてよい

データが存在し、場面上必要な場合は、次も評価対象にしてください。

- 誰を狙っているか
- 僚機との役割分担
- 指示との関係
- 重視点

「確からしさ」の表現は優先度を下げます。必須要素にはしないでください。

構造化出力を採用している場合は、単なる文字列検索ではなく、対応するフィールドの有無と内容を評価してください。自由文の場合は、ルール判定とJudge判定を分けてください。

## 2. 正しさ

時点ごとに判定内容を変えてください。

### 開始点

- これから何を、何のためにするかが説明されているか
- 説明した計画と、次の変化点までの実際の行動が一致するか
- 外的要因による妥当な計画変更後の行動を、開始時の予告との不一致として誤って減点しないこと

### 変化点

- 何が起きたかが、警報・指示・観測などの記録と一致するか
- 以前の計画から何を変更したかが説明されているか
- 新しい計画が、その後の記録と矛盾しないか

### 要求点

- 質問に対応する粒度で答えているか
- 回答が時刻 t 以前の記録と一致するか
- 記録から判断できない内容を、断定せず「分からない」と扱えるか
- 最新の説明と不必要に矛盾していないか

「RLモデルの本当の内的理由との一致」は、直接観測できない場合に正解として扱わないでください。観測可能な記録との整合、将来行動との整合、人による妥当性判定を分けて保存してください。

## 3. タイミング

### 開始点

- AIが行動する前、または人が介入できるだけの余裕を残して説明できたか
- 戦術の開始を検出してから説明を出すまでの遅延

### 変化点

- 報告すべき変化を見落としていないか
- 短い揺れや重複した変化を報告しすぎていないか
- 人が対応できる時点までに説明できたか

### 要求点

- 問いを受けてから2〜3秒以内に応答できたか

質問頻度は、最短10秒に1回程度を想定します。ただし、この値を固定ロジックへ埋め込まず設定値にしてください。

## 4. 判断への寄与

説明なしの場合と比べて、説明を読んだ人が次を行いやすくなるかを評価します。

- 自分の意図とAIの意図のずれに気づく
- 変化の理由を理解する
- 次の計画を理解する
- 指示が反映されたか確認する
- 任せる、確認する、指示する、の判断を改善する
- 要求点では、疑問が解消される

この観点はログだけで機械的に正解を決めないでください。人の評価または校正済みのLLM as a Judgeによる評価として、機械判定とは分離してください。必要な人評価データがない場合は、0点ではなく not_evaluated 相当として扱ってください。

## 人評価とLLM as a Judge

次の流れを扱える構成にしてください。

1. 人が4観点ごとに判定する
2. 判定結果と根拠を保存する
3. 人の判定を使ってルーブリックとJudgeを校正する
4. 校正後、同じ4観点をLLM as a Judgeで評価する
5. 人とJudgeの一致度を確認できるようにする

各評価結果には、少なくとも次を追跡できる情報を保存してください。

- 対象シナリオ、機体、時刻
- 開始点・変化点・要求点の区分
- Translatorへの入力範囲
- Translatorの元出力
- 軸別の判定結果
- 各判定の根拠
- 評価者の種類（機械、人、Judge）
- 使用したルーブリックと設定のバージョン
- Judgeを使う場合のモデル、プロンプト、実行条件
- 総合結果
- 評価不能またはデータ不足の理由

機械判定、人による判定、Judgeによる判定を同じ値で上書きせず、別々に保存してください。

## 未確定事項

次はまだ決まっていません。

- 戦術の語彙
- 戦術の開始・終了・切り替わりの区切り方
- 短い揺れを切り替わりに数えないための閾値
- 「間に合う」「出しすぎ」の具体的な閾値
- 1シナリオあたりの発言回数
- 機体ごとに説明するか、複数機をまとめるか
- 軸ごとのスコア尺度
- 4観点から総合点を作る方法
- Judgeを人の代わりに使ってよい一致度の基準

これらを独断で決めたりハードコードしたりしないでください。設定可能な形にし、未設定時の挙動を明示してください。データや合意がなければ not_evaluated、警告、TODOなど、既存設計に合う方法で未確定状態を保持してください。

## 実装方針

実装前に、対象リポジトリの AGENTS.md、README、既存の評価コード、データ形式、テスト方針を確認してください。既存の設計・命名・CLI・保存形式があれば、それを優先してください。

評価処理は、少なくとも次の責務に分離してください。

- 評価対象となる時点と区間の表現
- Translator入力の時刻範囲の検証
- 必須要素、遅延、発言回数などの機械判定
- 人評価の保存
- LLM as a Judgeの実行
- 軸別結果と根拠の保存
- 集計とレポート

既存実装に合わない場合は、上記のクラス名やファイル構成をそのまま採用する必要はありません。責務が分離され、後からルーブリックや閾値を変更できることを優先してください。

## テスト

最低限、次をテストしてください。

- 時刻 t より後の情報がTranslator入力に混入しない
- 未来情報の混入を検出できる
- 必須要素の欠落を検出できる
- 開始点・変化点・要求点で異なる評価規則が使われる
- 開始点の後に外的要因で計画が変わった場合、開始時の説明を不当に減点しない
- 記録にない内容を断定した回答を検出またはJudgeへ送れる
- 応答時間と発言頻度の設定値を変更できる
- 未確定の閾値が未設定でも、黙って恣意的な値を使わない
- 人評価とJudge評価が上書きされず別々に残る
- 評価不能が0点と区別される
- 既存テストがすべて通る

可能であれば、小さなfixtureを用意し、開始点・変化点・要求点を1件ずつ通した実行例も追加してください。
