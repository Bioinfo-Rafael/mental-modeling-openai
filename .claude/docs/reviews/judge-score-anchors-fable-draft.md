パケットで Judge が参照できる材料（この文書での略称）:
WINDOW（t-59〜t の軌跡。行動 id は A チームのみ記録、B チームは状態のみ）、OUTPUT（intent と evidence の自由文）、ALARMS / INSTRUCTIONS / QUESTION（発行ステップ付き）、PREVIOUS（同じ対象の直前の説明）、TIMELINE（同じ対象の説明の step・trigger 種別・`processing_s`）、FUTURE（開始点・変化点のみ。t+1 から次の外的要因の直前まで、5 ステップおき、同じ対象の後続説明の一覧付き）。
注意: Judge は annotation（`action_onset_step` など）を見ない。したがって Judge のタイミング判定は、パケット内で観測できる前後関係だけで書く。

## 1. 良いアンカーの条件（設計原則）

1. **各段階は「パケットのどこを見て、何を数えれば決まるか」で書く。** 形容詞（おおむね・軽微・十分）は条件の名前にはしない。条件は「引用できる語句があるか」「記録と不一致な主張の件数」「step の前後関係」「TIMELINE 上の件数」のどれかに落とす。
2. **一基準一軸、かつ「該当する最も低い段階が点数」。** 5→1 の各段階を欠陥の重さの順に書き、Judge は 1 から順に見て最初に該当した段階を採る（記述上は 5→1 で並べる）。この規則だけで、隣接段階の排他性と単調性が構成的に保証される。二軸が混ざる基準（変化点のタイミング: 遅れと出しすぎ）は、軸ごとに段階を割り当てて一本の梯子にするか、基準を分ける（§4）。
3. **3 と 4 の境界は「読み手の判断が変わるか」で固定する。** 評価者間の不一致が最も出る境界なので、観点ごとに一つのテストを決める。
   - 正しさ: *誰・何・どちら向き・原因* が合っていて *量・程度・時間表現* だけがずれる → 4。誰・何・向き・原因のどれか 1 件が違う／照合不能 → 3。
   - 要素: 要素を答える語句を OUTPUT から **そのまま引用できる** が一般的 → 4。引用できず、evidence や文脈から **推測** しないと読めない → 3。
   - タイミング: 説明が行動の **前か同時** → 4 以上。行動が **先に始まっている** → 3 以下。
   - 寄与: 説明 **だけ** で任せる・確認する・指示するのどれかを選べる（記録の確認は補助）→ 4。判断に必要な要素が 1 つ欠け、記録を読み直さないと決められない → 3。
4. **`cannot_judge` はパケットの欠落、`not_applicable` は場面の不要。説明の曖昧さはどちらでもなく低得点。**
   - `cannot_judge`: 判定に必要な記録がパケットに無い。例: FUTURE が「(no step inside the window)」、主張が B チームの行動 id に関するもので状態（yaw/alt/tas）からも判別できない、PREVIOUS が無いのに直前説明との整合を問われた。根拠に「何が無いか」を書く。
   - `not_applicable`: `conditional: true` の要素のみ。場面にその要素が存在しない。例: 単機対象で僚機が `alive=0`、INSTRUCTIONS が「none」、敵が全機 `alive=0`。
   - 説明が曖昧・一般的・空である場合は 1〜3 を付ける。「書いてないから判断できない」は `cannot_judge` ではない。
5. **根拠の定型（D67）。** 「該当: n。根拠: <step / 機体 id / 記録値 / 引用>。n+1 でない理由: <n+1 の条件のうち満たさない語句>」。段階の条件が観測可能なら、この二行は機械的に書ける。
6. **Judge のタイミングは順序と件数のみ、数値閾値（秒・ステップ）は機械判定に残す。** 未確定の閾値（`start_min_lead_steps` など、現在 null）を Judge のアンカーに埋めると、null の間は Judge が恣意的な値を使うか全件 `cannot_judge` になる。パケットで観測できる前後関係（行動の開始が t の前か後か、外的要因から t までの説明件数）だけで梯子を作れば閾値不要で判定できる。別案は §4。

## 2. 基準別アンカー（5→1、「該当する最も低い段階が点数」）

### 2.1 要素（`elements.*`、全時点共通）

共通の梯子。「具体的」の中身は下表で基準ごとに固定する。

| 段階 | 条件（OUTPUT の intent と evidence を見る） |
|---|---|
| 5 | 要素を答える語句を一文としてそのまま引用でき、下表の「具体」要件（固有名・方向・数値のいずれか）を含む。 |
| 4 | 引用できるが「具体」要件を含まない一般語のみ（例: 「接近する」「有利な位置を取る」）。 |
| 3 | intent に引用できる文がなく、evidence の記録値や前後の文から推測してはじめて読み取れる。 |
| 2 | 要素を示す語が 1 語程度あるだけで、文として述べていない（例: 「攻撃」の一語のみ）。 |
| 1 | 要素に触れていない。 |

| 基準 | 5 の「具体」要件 | 5 の例（LAG） | not_applicable |
|---|---|---|---|
| `elements.what_now` | 行動の種別 + 方向・高度・速度・対象のいずれか | 「B0200 に向けて右旋回しつつ高度を 6000 m まで下げている」 | なし（必須） |
| `elements.why` | 目的 + 近い将来の状況（位置関係・射程・回避） | 「背後から射程内に入り、先に発射できる位置を取るため」 | なし（必須） |
| `elements.target` | 機体 id または一意に定まる呼称 | 「B0100 を狙っている」 | 敵が全機 `alive=0`、または行動が敵と無関係（帰投・回避のみ） |
| `elements.wingman_role` | 自機と僚機それぞれの役割 | 「A0100 が B0100 を引きつけ、A0200 が側方から B0200 を狙う」 | 単機対象で僚機が `alive=0`、または対象がチームでなく僚機の記録が WINDOW に無い |
| `elements.instruction_relation` | 指示の語句への言及 + 従う／逸脱する | 「指示『B0100 を優先』に従い B0100 を追う」 | INSTRUCTIONS が none |
| `elements.priority` | 優先する価値 + 犠牲にする価値 | 「自機の生存より B0200 への接近を優先」 | 行動に選択肢がない場面（例: 回避のみ。評価者が判断） |

### 2.2 開始点（`start`）

**`correctness.start_plan`（これから何を、何のためにするか。WINDOW・INSTRUCTIONS と照合）**
- 5: 行動（何を）と目的（何のため）が両方引用でき、両方が WINDOW の位置関係・`alive`・INSTRUCTIONS と矛盾しない。
- 4: 両方引用できるが、一方が一般語（「有利な位置」「交戦」）で記録と照合できない。
- 3: 行動か目的の一方しか述べていない、または一方が WINDOW の記録と 1 件不一致（例: 「北へ向かう」だが WINDOW 最終行の `yaw_deg` は南へ変化中）。
- 2: 現状の描写のみで、これからの計画を述べていない。
- 1: 計画が記録と矛盾する（例: 「B0100 を攻撃」だが B0100 は WINDOW で `alive=0`）、または別の目的を述べている。

**`correctness.start_future`（計画と FUTURE の行動の一致。FUTURE 使用可）**
- 5: 説明した行動の要素（方向・高度・速度・対象への接近）がすべて FUTURE の `*_action_id` または状態の推移で確認でき、不一致なし。
- 4: 主要素は確認できるが、量・程度の表現が 1 件ずれる（例: 「急降下」だが `altitude_action_id=2` は 1 行のみで `alt_m` の減少は 200 m）。
- 3: 方向・高度・速度・対象のどれか 1 要素が FUTURE と不一致（例: 「右旋回」だが `heading_action_id` は 0/1 が続く）。
- 2: 2 要素以上が不一致。
- 1: FUTURE の行動が説明と反対、または説明した行動が FUTURE 内で一切始まらない。
- `cannot_judge`: FUTURE が空、または対象が B チームで状態の推移から判別できない。FUTURE の終端より後の行動は根拠にしない。

**`timing.start_in_time`（行動の前、または介入の余裕。WINDOW・TIMELINE・FUTURE 使用可）**
- 5: 説明した行動が t 時点で未開始（WINDOW の最終 5 行に該当する行動 id・状態変化がない）で、FUTURE の中で始まる。
- 4: 説明した行動が t（`a_t`、D58 で t 以前扱い）または t-1 で始まっている。
- 3: 行動が t より前に WINDOW 内で始まっており、t 時点でまだ続いている。
- 2: 行動が WINDOW の開始（t-59）より前から続いている（WINDOW 全体がその行動中）。
- 1: 行動が WINDOW 内で始まり、t までに終わっている（FUTURE に続きがない）。
- 注: 「開始点の見落とし」は事象が無いので Judge では採点できない。機械判定（annotation との照合）の領分。

**`contribution.*`（開始点・変化点・要求点共通の梯子。「判断」は下表の通り）**
- 5: 説明だけで判断でき、判断の理由を OUTPUT の語句で引用できる。誤解を招く記述がない。
- 4: 説明だけで判断できるが、確認のため WINDOW または記録を 1 箇所見直したくなる（説明がやや一般的）。
- 3: 判断の方向は示されるが、判断に必要な要素（誰・何・なぜ・いつまで）が 1 つ欠け、記録を読み直さないと決められない。
- 2: 説明を読んでも読まなくても判断は変わらない（一般的な言い回しのみ）。
- 1: 説明が判断を誤らせる（記録と反対の方向を示す、無い指示の反映を主張する）。

| 基準 | 「判断」の中身 | 5 の例 |
|---|---|---|
| `contribution.intent_gap` | 自分の意図と比較できる形で AI の選択が書かれているか | 「指示通り B0100 を優先し、B0200 は A0200 に任せる」（何を選び何を捨てたか） |
| `contribution.next_plan` | 次に何が起きるかを一文で言えるか | 「射程に入ったら発射、外れたら左旋回で離脱」 |
| `contribution.delegation` | 任せる／確認する／指示する のどれかを選べるか | 行動・対象・目的・条件が揃い、追加質問なしに「任せる」と決められる |
| `contribution.change_reason` | 変化の原因を一文で言えるか | 「ミサイル警報（step 312）を受け、接近を中断して降下回避に切り替えた」 |
| `contribution.instruction_reflected` | 指示が反映されたか／されなかったかを確認できるか | 「指示『B0100 を優先』は反映済み。B0100 への接近を継続」 |
| `contribution.question_resolved` | 質問者の疑問が消えるか | 質問「なぜ左旋回？」→「B0200 の後方に回り込むため。B0100 は A0200 が担当」 |

### 2.3 変化点（`change`）

**`correctness.change_cause`（何が起きたか。ALARMS・INSTRUCTIONS・WINDOW と照合）**
- 5: 原因が ALARMS / INSTRUCTIONS / WINDOW の記録と一致し、step または内容で特定できる（例: 「step 312 のミサイル警報」）。
- 4: 原因の種類は一致するが、どの記録かが特定されない、または時刻表現が 1 件ずれる。
- 3: 原因の種類が記録と違う（警報を指示と述べる）、または記録に無い原因を 1 件挙げる。
- 2: 記録にある原因を挙げず、記録に無い原因を 2 件以上挙げる。
- 1: 原因に触れない、または記録と反対の原因（警報が出ていないのに「警報で」）。
- `cannot_judge`: 原因候補が WINDOW の観測事象（敵の発射など）で、WINDOW にその事象が映っていない。

**`correctness.change_delta`（以前の計画から何を変えたか。PREVIOUS と照合）**
- 5: 変更前（PREVIOUS の語句）と変更後の両方を述べ、変更前が PREVIOUS と一致する。
- 4: 変更後は具体的だが、変更前は一般的な言及のみ（「接近をやめ」）。
- 3: 変更後のみを述べ、何から変えたかが無い。
- 2: 変更前後が区別できない（新しい計画が PREVIOUS と同じ内容）。
- 1: 変更前として述べた内容が PREVIOUS と矛盾する。
- `cannot_judge`: PREVIOUS が none。

**`correctness.change_future`（新しい計画と FUTURE の整合。FUTURE 使用可）**
- `correctness.start_future` と同じ梯子を使う。1 の追加条件: FUTURE 内で PREVIOUS の行動に戻っている（変化を述べたが変化していない）。

**`timing.change_in_time`（間に合ったか、出しすぎていないか。TIMELINE・FUTURE 使用可）**
s = 原因の step（ALARMS / INSTRUCTIONS の発行 step、観測事象なら WINDOW で初めて映る step）。
- 5: s 以後、同じ対象の説明は t が最初（TIMELINE で s<step<t の件数 0）で、新しい行動が WINDOW 内で t より前に始まっていない。
- 4: t が s 以後の最初の説明だが、新しい行動は t より前に WINDOW 内で始まっている（後追いだが最初の報告）。
- 3: s<step<t に同じ対象の説明が 1 件ある（1 回見送ってからの報告）、または t の説明が同じ変化の 2 回目の報告（TIMELINE か FUTURE の後続一覧に同じ原因の change が 1 件）。
- 2: s<step<t に説明が 2 件以上、または同じ変化の 3 回目以上の報告。
- 1: 報告した変化が FUTURE 内で PREVIOUS の行動に戻る短い揺れ（持続しない）。
- 注: 「変化の見落とし」は事象が無いので Judge では採点できない。機械判定の領分。

### 2.4 要求点（`request`。FUTURE なし）

**`correctness.question_granularity`（質問に対応する粒度）**
- 5: 質問の問いの型（なぜ／何を／誰を／いつまで）に直接答える文が OUTPUT の先頭にあり、問われていない話題を加えていない。
- 4: 直接答えているが、答えが文中に埋まっている、または余分な一般説明が付く。
- 3: 質問の一部にしか答えていない（2 点聞かれて 1 点）、または粒度が合わない（「なぜ」に「何をしているか」で答える）。
- 2: 質問と無関係な現状説明のみ。
- 1: 回答がない、または質問を取り違えている（別の機体について答える）。

**`correctness.records_to_t`（t 以前の記録との一致）**
- 5: 照合可能な主張がすべて WINDOW・ALARMS・INSTRUCTIONS と一致し、照合不能な断定がない。
- 4: 照合可能な主張はすべて一致するが、量・程度・時間表現が 1 件ずれる（例: 「高度を大きく下げた」だが `alt_m` の差は 100 m）。
- 3: 誰・何・向き・原因のどれか 1 件が記録と不一致または照合不能。
- 2: 2 件以上が不一致。
- 1: 主目的が記録と矛盾する、または別の対象について述べている。

**`correctness.unknown_not_asserted`（分からないことを断定しない）**
- 5: 記録で確認できない内容を述べていない、または述べる場合は「不明」「推定」と明示している。
- 4: 推定であることは読み取れる（「〜とみられる」）が、明示語がない。
- 3: 記録で確認できない断定が 1 件（例: 「B0100 は燃料切れで離脱」—燃料は記録にない）。
- 2: 2 件以上。
- 1: 質問への答えそのものが記録にない断定（例: 敵の意図を事実として断定）。

**`correctness.consistent_with_latest`（最新の説明と不必要に矛盾しない）**
- 5: PREVIOUS と矛盾なし、または矛盾する点は新しい外的要因（PREVIOUS の step 以後の ALARMS / INSTRUCTIONS）を挙げて更新している。
- 4: 表現が違うが意図（行動・対象・目的）は同じ。
- 3: 行動・対象・目的のどれか 1 件が PREVIOUS と違い、理由を述べていない。
- 2: 2 件以上違い、理由がない。
- 1: PREVIOUS と反対の意図を、新しい要因なしに述べている。
- `cannot_judge`: PREVIOUS が none（→ §4: この基準を `conditional` にして `not_applicable` を許す案）。

**`timing.request_in_time`（十分速く応答。TIMELINE の `processing_s`、QUESTION の step）**
既存の設定値だけを使う: `request_deadline_s`（3.0）、`min_question_interval_s`（10.0）。
- 5: `processing_s` ≤ `request_deadline_s` かつ t が QUESTION の step と同じ。
- 4: `processing_s` ≤ `request_deadline_s` だが t が QUESTION の step より後（次のティックで応答）。
- 3: `processing_s` > `request_deadline_s` だが、QUESTION の step からの経過 + `processing_s` < `min_question_interval_s`。
- 2: 経過 + `processing_s` ≥ `min_question_interval_s`（次の質問の時刻までに返せていない）。
- 1: 応答が無い（TIMELINE に `processing_s` が記録されない、またはタイムアウト）。

**`contribution.question_resolved` / `contribution.delegation`**: §2.2 の共通梯子。

## 3. D29 総合 1–5（`rendering.py`、キーポイント 0/1/2 と併用）

キーポイント（KP）が与えられたときは KP の得点で、与えられないときは「主目的」「主行動」の 2 点を暗黙の KP として同じ条件を適用する。

- 5: すべての KP が 2、かつ材料と矛盾する主張が 0 件。
- 4: すべての KP が 1 以上で、1 が 1 件以下、かつ矛盾 0 件。
- 3: KP に 0 が 1 件、または 1 が 2 件以上、または主目的・主行動以外の細部に矛盾 1 件。
- 2: KP の過半が 0、または主行動が材料と矛盾。
- 1: 主目的が材料と矛盾する、別の目的を述べている、または intent が空。
- 根拠は D67 と同じ定型（該当段階、根拠、上の段階でない理由）。

## 4. リスク / ユーザーが決めること

1. **タイミング基準と null の機械閾値の関係。** 本案は Judge のタイミングを前後関係と件数だけで定義し、秒・ステップの閾値（`start_min_lead_steps`、`change_max_delay_steps`、`max_events_per_segment`）は機械判定に残す（§1.6）。別案: アンカーに設定キーをそのまま埋め、null の間は Judge がその基準を `cannot_judge` にする（機械側の `not_evaluated/<key>_unset` と同じ扱い）。前者は閾値未定でも採点でき、後者は人と Judge が同じ数値で揃う。どちらにするか。
2. **二値に近い基準に 1–5 は細かすぎる。** `elements.*`、`unknown_not_asserted`、`consistent_with_latest`、`instruction_reflected` は実運用で 5/3/1 に偏り、2 と 4 はほぼ使われない見込み。簡潔さ（D59・D65）を優先して尺度は全基準 1–5 のまま、パイロット後に分布を見て 3 段階へ畳むかを判断する、を推奨。今決めるなら「全基準 1–5」か「基準ごとの `values` 指定」か。
3. **`timing.change_in_time` は遅れと出しすぎの二軸。** 本案は 5/4 を遅れ、3/2 を見送り・重複、1 を揺れに割り当てて一本化したが、「遅れなし・重複 1 回」と「1 回見送り・重複なし」が同じ 3 になる。気になるなら `timing.change_delay` と `timing.change_overreport` に分ける（基準が 1 件増える）。
4. **`consistent_with_latest` と `change_delta` は PREVIOUS が none のとき判定不能。** `cannot_judge`（not_evaluated）で残すか、`conditional: true` にして `not_applicable` を許すか。前者は初回説明が毎回 not_evaluated として積み上がる。
5. **B チーム対象の FUTURE 基準。** B チームの行動 id は未記録のため、`*_future` は状態（`yaw_deg`、`alt_m`、`tas_mps`）の推移のみで判定する。状態からも判別できない主張は `cannot_judge`。これで良いか（B チームは評価対象から外すという選択もある）。
6. **「該当する最も低い段階」規則の明文化。** 本案の排他性・単調性はこの規則に依存する。`scale` の冒頭（人向け・Judge 向け共通）に一文で書く必要がある。
7. **寄与の 3/4 境界は「説明だけで決められるか」。** D57 のとおり対照実験なしの単独評価なので、この境界はテストとして書いても評価者の主観が残る。パイロットで人同士の一致度（重み付きカッパ）を見て、必要なら 4 の条件に「確認箇所 1 箇所」のような件数を入れる。
8. **`elements.priority` の not_applicable 条件は評価者判断を含む。** 「選択肢のない場面」を機械的に定義できない。緩めるなら「常に採点（低得点可）」に戻す。
