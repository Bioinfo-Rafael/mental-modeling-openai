## 背景・目的 (Background & Purpose)

<!-- Why does this project exist? What problem does it solve, for whom?
     State the business/technical context and the goal in a few sentences. -->

Research code that translates the behaviour of reinforcement-learning agents into intent statements with LLMs and evaluates those translations with LLM-as-a-judge. The core is two packages: `src/translate`, one config-driven causal loop (select inputs -> each input renders View(t) -> fill the inline prompt -> one call) whose trigger points are start (step 0), request (a human question) and change (preset steps or the clef-flash detector), and `src/evaluation`, one judge engine that rates every translation on the criteria of its point kinds from the same human-visible material. The legacy LLM-Xavier work (Lu et al., TMLR 2024: mental modelling, few-shot prompting, reward ablation, in-context RL, LAG trajectories) is kept, not deleted, as the independent `workspace/` project, which is also the free-experiment area. The core and `workspace/` do not depend on each other.

## スコープ (Scope)

### In Scope

<!-- What this project explicitly delivers. -->

- `src/translate`: one translation loop (2026-11-09 simplification). A run config (`configs/translate/*.yaml`) selects the inputs (instructions, alarms, question, recent messages, previous translation, trajectory, policy trace), holds the prompt text inline, and names the change source: `preset` steps or `clef_flash` (the System One detector on its tick grid). `start` (step 0) and `request` (a human question) are forced; instructions and alarms are prompt context and detector input only.
- `src/evaluation`: one judge engine (`python -m evaluation judge | import-ratings | report`) with its prompt and criteria inline in `configs/evaluation/judge.yaml`, a causality audit of the run's journaled requests, human ratings and a report (cells, weighted kappa, the D55 deadline).
- MHI v1.3 match data in `data/mhi/` (read-only) and Slurm jobs in `slurm/` (`common.sh`; MODE `preview`/`paid`, `probe`/`paid` for the online job; `slurm/lag/` for rollout recording and episode preparation; logs in `logs/slurm/`).
- `workspace/`: an independent uv project (own `pyproject.toml`, `uv.lock`, `.venv`) with the legacy LLM-Xavier experiments 00-17, the vendored `src/mentalmodeling`, and the `mtd_rl_xavier_workspace` legacy library (experiment, preprocessing, datasets, tools, lag batch). It reads only `../data/mhi` from outside and is the place for free experiments. The core does not guarantee it.

### Out of Scope

<!-- What is explicitly NOT covered, to prevent scope creep. -->

- Training RL policies. Live environments run only to record or replay rollouts of existing LAG checkpoints (`scripts/lag/record_rollouts.py` runs `MultipleCombatEnv`, `scripts/lag/replay_episode.py`) with the external mtd-rl-lag interpreter, never inside the core `.venv`.
- Importing or reading `workspace/` from the core, or importing the core from `workspace/`. Legacy LLM-Xavier experiments are not part of the core's tests, jobs or guarantees.
- Weights-only policy explanation (the former `weightreading run/evaluate`) and local vLLM chat (`llm/vllm_chat.py`): both deleted 2026-11-08. The sandboxed policy code session, the D29 key-point judge, the viewer, the clip tool and the byte-identity machinery: deleted 2026-11-09.

## アーキテクチャ (Architecture)

<!-- High-level architecture: components, data flow, boundaries.
     Add a diagram or description here. -->

### Agent Roles

| Agent | Role | Responsibilities |
|-------|------|------------------|
| Change-point detector (System One model on local vLLM) | Translator layer 1 | Each tick, decide none / change for a target from its state text (previous intent, instructions, recent alarms and questions, a short trajectory window) at or before t |
| Translation model (OpenAI Responses) | Translator layer 2 | Write the intent statement for a target at start, at a human question and at a change |
| Judge (OpenAI Responses, gpt-6.1-sol) | evaluation/ | Rate each translation event on the criteria of its point kinds, with a rationale per criterion |

- The loop (src/translate/pipeline.py) writes events.jsonl/requests.jsonl/responses.jsonl (event schema 3) for every configuration; each translation event records the human-visible material (instructions, alarms, question, previous translation, trajectory window) whatever the translator read, and the judge (src/evaluation/) renders the same material for every event; design: .claude/docs/plans/xavier-simple-design-final.md (in the orchestration workspace).

## 制約 (Constraints)

<!-- Technical, organizational, regulatory, or resource constraints. -->

- Saved results are immutable; the ones already tracked in git stay as they are (no history rewrite). New large generated artifacts go to Git LFS or external storage, not plain git (location TBD). Saved legacy results record repo-relative paths in the pre-restructure layout; `workspace/` resolves them with `mtd_rl_xavier_workspace.paths.resolve_recorded`.
- Dependency direction: the core never imports or reads `workspace/`; `workspace/` never imports the core and reads only `../data/mhi`. `evaluation` imports `translate`, never the reverse. In `workspace/`, plans refuse to reuse, resume or merge results produced under different prompt/scoring code (`semantics_sha256`).
- Paid API in the core: every entry point previews by default and needs `--execute --confirm-paid-api`; Slurm MODE `paid` adds both flags and `preview` drops any inherited `OPENAI_API_KEY`. The key lives in the gitignored, group-shared repo-root `.env` (mode 0660 on purpose) and is loaded only right before a paid submission. Legacy entry points in `workspace/` are weaker (09-12 send with no arguments; 14-17 send Batch requests with `--execute` alone); see `workspace/README.md`.
- Legacy `workspace/` experiments need `data/llmx_data` at revision `dc2b798f72bc02f7285949ccfcdcb42e5ff326fd` (downloaded locally, gitignored). The core needs only `data/mhi/` (read-only).
- The host is a Slurm login node: heavy work runs as Slurm jobs submitted from the repository root; the login node is for editing and git only.
